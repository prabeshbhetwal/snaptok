# Android 0.6.1 — TikTok Share-control recognition

## Confirmed cause

On the connected Samsung Galaxy S24 Ultra (Android 16), TikTok 47.1.4 exposes the video Share button with content description **Share video 25K shares**. SnapTok 0.6.0 accepted only exact labels such as **Share video**, so it rejected the visible control before opening the sharing panel. This was a selector failure, not a download-engine failure or a missing Accessibility grant.

The live sharing panel exposes an enabled, clickable button with content description **Copy link**, plus a child text label for that same button. They represent one action and must be deduplicated. No contact names or caption text are retained in this report.

## Changes

- Recognise the entire observed Share label, including a numeric share-count suffix. Matching stays anchored: captions, profile sharing and recipient actions are rejected.
- Honour explicitly labelled Android accessibility actions and advertised click actions, including actions on the root container.
- Normalise line breaks and non-breaking spaces in recognised labels.
- Wait within the existing bounded capture timeout for delayed controls. Missing controls no longer fail on the first tree read; ambiguity still fails immediately.
- Retain TikTok package restrictions, user-triggered capture, one-use handoffs and fresh-clipboard validation. No coordinate-based fallback or additional permissions are introduced.

## Validation

The regression suite covers the exact on-device description, counted-label rejection cases, labelled custom actions, advertised click actions without a clickable flag, delayed controls and bounded timeout. The existing copy/clipboard and safety tests remain part of the full run.
